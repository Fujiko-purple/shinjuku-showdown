## 0. 我的结论（先回答你问的"你认为呢"）

**同意重做。但不是"推翻一切"，而是"换心脏、换骨架，保留器官"。**

具体判断分三条：

1. **朋友骂得对，而且他骂到了根上。** 他说"不要加机制、要加攻击欲望/防御/伤害/降低容错"，这句话的工程含义是：
   现在的 demo **没有核心循环**。玩家做任何操作都不会改变战斗的走向 —— 跑图不掉收益、闪避不创造回合、领域对拼赢了只少掉 32 点血（对 1800 血池 = 1.8%）。
   一堆机制（魔虚罗适应 / 领域同步轴 / 黑闪 ±16.7ms / 疾跑）都是**平行叠加**的独立小游戏，它们不互相咬合，也不服务同一个循环。
   这不是"数值没调好"，是**结构问题**。结构问题在原结构里修补，只会越补越像现在的样子。

2. **但现在的工程里有三块资产不该重做**（重建 = 白扔 2~3 周）：
   - **场景与特效管线**：新宿街区（city.js）、特效（fx.js）、武器与领域视觉（weapons.js）、程序化音频（audio.js）—— 它们的问题只是"用得太多、没有预算"，不是"不对"。
   - **角色模型**：魔虚罗这一版是按官方立绘重做的、五条/宿傩的绑定也在；缺的是**动画与剪影规范**，不是从零建模。
   - **验证与发布体系**：CDP 探针（40+ 个）、构建管线、Cloudflare Pages 部署 —— 这是这个项目最被低估的资产，重做项目最容易死在没有验证手段上。

3. **新项目应该"新仓库 + 新内核 + 复用资产"**：
   - 新目录 / 新仓库（名字见 §7.1），构建仍是"多文件源码 → 单文件 HTML 产物 + 静态站"。
   - **重写**：战斗内核（固定帧 + 帧数据表 + 状态机 + 判定）、BOSS AI、玩家资源系统、HUD、关卡流程。
   - **搬过去**：city / fx / weapons / audio / 角色模型 / 构建 / 探针 / 部署。
   - **删掉不回迁**：HOOKS 插件总线（它是"各自为政"的温床）、领域同步轴小游戏、魔虚罗血条、现在的 HUD 布局。

## 1. 诊断：为什么现在这个不好玩（把吐槽翻译成设计问题）

朋友的 8 条吐槽，每一条都能落到一个具体的机制缺陷上。我把它们和代码事实对上：

| # | 他的原话 | 设计诊断 | 代码事实 |
|---|---|---|---|
| 1 | 「上强度是加 BOSS 攻击欲望/防御/伤害、降低玩家容错，不是加机制，加机制叫粪怪」 | **难度应该来自"同一个规则下更紧的执行"，不是"更多规则"**。每加一条新规则，玩家要学的东西+1，但已有的技术没有变强 | 上一轮一次加了 4 个机制（魔虚罗 / 领域同步轴 / 黑闪 / 疾跑），它们之间没有耦合 |
| 2 | 「跑图没收益，跑反而掉血，站着不动最好」 | **距离不是资源**。撤退本应是"重置节奏、诱招、回资源"，但这里只有惩罚 | 宿傩「解」= 0.32s 后线段必中（判定半径 1.35m）；领域「伏魔御厨子」半径 90m，等于无处可躲 |
| 3 | 「无下限还有后摇卡自己，躲不掉的」 | **防御动作没有收益**：闪避只"抵消"，不创造回合；而且有无敌帧成本（CD 1.25s）却没有任何回报 | 空格 = 0.4s 免伤 + 16m 位移，CD 1.25s，之后没有任何强化窗口 |
| 4 | 「一个术式回转就把魔虚罗技能全吃了；宿傩在下面被抽成陀螺」 | **注意力与资源被小游戏抢走**，主战斗反而变成背景 | 魔虚罗在场时玩家打宿傩只有 ×0.6；玩家最优解是"无视魔虚罗" |
| 5 | 「魔虚罗没必要设血量，反正又不用肘他」 | **错误的机制载体**：原作里魔虚罗没有血条，只有"再转几次就适应完成"的倒计时 | 代码：HP 900，近战一下 27，理论上要 33 下 |
| 6 | 「领域破掉没有任何收益；我为什么要玩那个小游戏」 | **博弈没有回报**：赢了对宿傩 32 伤害（1800 血的 1.8%），输了自己 36 伤害 | 代码：CLASH_WIN_DMG = 320/360，再过 INCOMING_SCALE 0.1 |
| 7 | 「判定瞎搞、BOSS 复读、躲不掉」 | **不存在"读招—应对"的信息链**：预警有，但应对没有唯一解也没有明确奖励 | 「空间斩」不可格挡、只能靠 invT；「开」爆炸半径 6m 且不可格挡 |
| 8 | 「画面很乱」 | **没有视觉预算**：颜色族、特效层数、UI 区域都没有上限 | 同屏同时可能有：领域球 + 领域对撞 + 魔虚罗法轮 + 黑闪 + 伤害数字 + 4 套 UI |

再补三条**代码层面**的、朋友看不到但同样致命的问题：

9. **伤害经济崩了**：玩家轻击对宿傩 = 26 × 0.6(庇护) × 0.1(全局系数) = **1.56 伤害**，对 1800 血池要 1154 下；而同样一拳对魔虚罗是 27（差 17 倍）。玩家根本感受不到"打击有分量"。
10. **逻辑与表现绑死**：主循环是可变时间步（sdt = dt × scale），hitstop/slowmo 会改写时间轴，逻辑层还有 Math.random —— 这既让手感不可调（顿帧与判定耦合），也堵死了联机（详见 \`research/D-netcode.md\` §3.2）。
11. **扩展方式是"加插件"而不是"加数据"**：contract.js 的 HOOKS 总线让 4 个机制各写各的文件、各建各的 HUD、各注册各的判定 —— 工程上很干净，**玩法上就是四个互不相干的小游戏**。

**一句话总结诊断：现在的 demo 是一个"机制展示厅"，不是一个"游戏"。**

## 2. 重制目标与四条设计支柱

**目标（一句话）**：把"机制展示厅"变成**一场可以反复挑战、每次失败都知道自己错在哪的 BOSS 战**，并且这一战里的每个动作都像原作里的那两个人。

| 支柱 | 含义 | 反面（现在的样子） |
|---|---|---|
| **P1 见招拆招** | 每一个伤害都有 ≥1 种"零伤害解法"；每一招都有 0.3s 以上的可辨预警；每一种正确应对都给资源/位置/伤害回报 | 「解」线段必中、「空间斩」只能硬吃 |
| **P2 距离是资源** | 拉开距离 = 重置节奏的中立选择（不涨资源、但也不额外掉血）；站对距离能提高输出（适正距离带） | 跑图 = 纯亏损（BOSS 全射程覆盖） |
| **P3 操作有收益** | 招架/完美闪避/黑闪/连段各自返还明确资源；**不存在"成功但无收益"的防御** | 闪避只抵消；连段只弹个数字 |
| **P4 人设还原** | 非对称对等：双方各握一个"对方必须专门回答的问题"；招式名、视觉、节奏都对着原作做 | 魔虚罗血条、"适应完成=无敌"、领域同步轴小游戏 |

**平衡的判据（来自原作考据 §5.4）**：不要追求"数值相等"，要追求**双方各有一个对方答不出的问题**：
- 五条问宿傩的问题：**无下限怎么破？**（原作的三个答案：领域展延 / 开放领域从外部侵蚀 / 世界斩）
- 宿傩问五条的问题：**领域与黑闪的爆发怎么扛？**（原作的答案：反转术式续航 / 魔虚罗适应 / 藏招换阶段）

## 3. 战斗内核（重写部分，新项目的地基）

### 3.1 三件必须先落地的基础设施

1. **固定 60Hz 逻辑帧 + 输入包 + sim/view 分离**
   理由不只是联机（\`research/D-netcode.md\` §3.2）：现在 hitstop/slowmo 直接改时间轴，导致"顿帧越强，判定越飘"，手感根本没法调。
   做法：逻辑层只吃"帧号 + 输入快照"，表现层（相机/FX/音频/震屏）订阅逻辑事件。表现层可以各自随机，逻辑层必须定种子。
2. **招式帧数据表（JSON/TS 数据，不是代码分支）**
   每招一行：起手 / 判定 / 后摇 / 伤害 / 判定盒 / 解标签(def) / 削韧 / 取消窗口 / 位移 / 音效 / 镜头。**新增招式 = 新增一行数据**，而不是新增一个模块（这是对 HOOKS 插件总线的直接修正）。
3. **判定与表现的事件化**
   所有"打到了/被招架了/自适应了"都发事件，HUD、音效、镜头、探针都从事件订阅。这样探针能直接断言"第 N 帧发生了什么"，而不是靠读内部变量。

### 3.2 玩家资源模型（只保留一条主资源，避免"机制堆砌"）

主资源：**咒力**（一条槽，双向）。

| 事件 | 咒力 | 附加 | 依据 |
|---|---|---|---|
| 轻击命中 | +3 | — | 本作已有 CE_ON_HIT 1.5 |
| 重击命中 | +5 | — | 设计推断 |
| **招架成功（无下限精准格挡）** | **+12** | 削韧 +18；打开 0.35~0.5s 反击窗口；0.2s 顿帧 | 只狼弹反 |
| **完美闪避**（无敌帧前半段穿过攻击） | +6 | 可选 0.2s 慢镜 | 设计推断 |
| 格挡成功 | −6 | 减伤部分转入"回气池"，3s 内攻击可回收 | Lies of P |
| 受到伤害 | −8 | 5s 内反击可回收最后一次伤害 | 血源 Rally |
| **距 BOSS > 12m 且 3s 无交锋** | **−3/s** | 取代现在的自然回复 6/s | 直接回应"跑图没收益" |
| 削韧打满 | 处决窗口 1.0s，伤害 8~12% 最大生命，**由玩家主动触发** | 只狼忍杀 |
| 三连段完成 | +8 | 让连段计数真正有收益 | 设计推断 |

> 反向设计：资源见底时不做"罚站"，而是**让防御变贵**（咒力 <20 时闪避后摇 +0.1s、格挡减伤下降）。

### 3.3 一次交互的"重量"标定（现状最大的病）

| 指标 | 现状（实测） | 新目标 |
|---|---|---|
| 玩家一次轻击 | 宿傩 1800 血的 **0.2%**（1.56 伤害） | **1.0~1.5%** |
| 一套三连段 / 招架反击 | — | **3~8%** |
| BOSS 一次普通命中 | — | 玩家血量的 **10~18%**（能承受 6~10 次失误） |
| BOSS 一次大招命中 | **5.5%** | **25~40%**（失误后还能继续，但压力明确） |
| 一局的读招-惩罚循环 | 数百次平A | **15~30 次** |
| 被同一次连段打死 | **可能发生** | **禁止**（受击后 ≥0.4s 脱离窗口） |

### 3.4 十二条战斗规则（新项目的"宪法"，每条都可脚本验收）

直接采用 \`research/C-souls-design.md\` §6 的清单，作为新仓库的第一份契约文件：

1. 每一招必须标注**能被哪些选项解**（招架/闪避/格挡/位移），且至少一种解法是"零伤害"。
2. 不可格挡/不可闪避的招必须给 **≥0.8s** 专属预警，且类型可辨（颜色 + 音效 + 剪影至少两项）。
3. 玩家必须有 **≥3 个防御动词**，代价互不相同（闪避=位置+后摇 / 招架=窗口+失败惩罚 / 格挡=资源消耗）。
4. 招架成功必须返还 ≥1 项资源并打开 ≥0.35s 反击窗口；**不允许"成功但没收益"的防御**。
5. 取消被动资源回复：资源只在距敌 12m 内的交锋中增长，>12m 时 −3/s。
6. 玩家冲刺速度 ≥ BOSS 常速 ×1.2；BOSS 后撤/位移期间**禁止攻击**。
7. BOSS 单次无敌/位移 ≤0.25s，霸体招占比 ≤30%；玩家完整三连段必须能推动削韧条。
8. BOSS 攻击间隔按阶段设下限：**P1 ≥2.2s / P2 ≥1.6s / P3 ≥1.1s**；难度只调**间隔与招式种类**，不调伤害。
9. 禁止同招连续复用：同一招冷却 ≥5s，且不得连续使用两次。
10. AI 只读动画与实体，**禁止读按键**；反应延迟 ≥0.2s。
11. 每招必须有 **≥0.5s 的空招惩罚窗口**，玩家能在其中塞进一整段反击。
12. 每一次交互都要有重量：轻击 1~1.5% BOSS 血，大招命中 25~40% 玩家血，一局 15~30 次读招循环。

> 这 12 条里，第 1/4/5/8 条分别直接回答朋友的「跑图没收益」「无下限没收益」「加机制不加强度」「BOSS 复读」。

## 4. 角色设计

### 4.1 五条悟（玩家侧）

**设计定位**：高技术上限的"术式 + 体术"混合角色。他的"最强"不体现在数值，而体现在**选项多、收益高、但每个选项都有窗口与代价**。

| 招式 | 键位 | 原作依据 | 新设计 | 与旧版的差别 |
|---|---|---|---|---|
| 体术三连 | J | 呪力操作与体术（原作他靠体术与宿傩对拳） | 三连段，第三段削韧高；第三段后可接招式取消 | 保留，但伤害按 §3.3 重标定 |
| 重击/踢 | K | 同上 | 高削韧、慢、有 whiff 惩罚 | 保留 |
| **术式顺转「蒼」** | U | 吸引（负压） | **拉近**：把 BOSS 拉出防御/拉进适正距离；可蓄力；对魔虚罗是"把它拽下来"的手段 | 旧版只有个 0 伤害力场 |
| **术式反转「赫」** | I | 斥力冲击波 | **击退 + 破防**：把 BOSS 推离/打断起手；有适正距离带（8~18m 满伤） | 旧版是纯伤害弹 |
| **虚式「茈」** | O（蓄力） | 湮灭 | 高伤直线，**只能在破防/硬直窗口命中**（移动中的 BOSS 会闪） | 旧版是万能高伤 |
| **无下限（防反）** | 空格 | 不可侵 / 距离内侧减速 | **按住 = 展开减速场**（消耗咒力，近身物减速）；**精准时机按 = 招架**（弹开 + 咒力返还 + 反击窗口） | 旧版是"0.4s 无敌 + 1.25s 空窗"，无收益 |
| **领域展延** | 新键或组合 | 中和对方术式、只能肉搏 | 短时**免疫必中类攻击**，但期间禁用术式 | 全新，也是"宿傩问五条的问题"的答案 |
| **黑闪** | V / 自动 | 误差 1e-6 秒内的打击 | **3 帧判定 → ×2.5 + 10s zone**（zone 内招式更快、咒力更省）；可练、不随机 | 旧版是 ±16.7ms 的 QTE，太窄且无 zone 概念 |
| **反转术式** | H | 治疗 | 咒力换血，施术期间不能移动（风险明确） | 保留，但要能与"被打断"博弈 |
| **无量空处** | G | 领域 | **不再是对拼小游戏**：展开后 BOSS 在领域内**冻结/行动不能**，但宿傩的**开放领域会从外部侵蚀**，玩家必须在"领域被侵蚀完"之前打出足够伤害或击破结界锚点 | 旧版：按 J 对齐指针的 12s 小游戏 |

### 4.2 宿傩（BOSS 侧）

**设计定位**：会"读你的习惯"的压迫者。他的强度来自**压迫节奏 + 招式的组合与惩罚**，不是来自"你没见过的机制"。

| 招式 | 原作依据 | 设计 | 玩家解法（必须 ≥1 种零伤害解） |
|---|---|---|---|
| **解**（远程斩） | 通常斩击 | 横向/斜向斩击波，**有明确飞行轨迹**（可走位穿过间隙） | 走位 / 闪避 / 招架 |
| **捌**（贴身斩） | 按对象调整的斩击 | 近身三连，最后一下可被打断 | 招架 / 后撤 / 打断 |
| **開・竈**（火焰箭） | 火焰弓 | 蓄力 0.8s，落点预警圈，**只在玩家站定时高命中** | 侧移 / 闪避 / 领域展延 |
| **伏魔御厨子**（开放领域） | 开放领域可被外部破坏 | 展开后持续斩击；**结界锚点暴露在外**，玩家跑到外沿打破锚点即可解除 —— 这比"对拼小游戏"好玩一个数量级，也完全是原作机制 | 打破锚点 / 领域展延 |
| **魔虚罗**（十种影法术） | 适应 | **适应进度条**（无血条）：它观察你的招式类型，逐项适应；被打断会给玩家大收益 | 换招 / 在适应完成前打出高强度一击 |
| **世界を断つ斬撃** | 学自魔虚罗的适应成果 | **一次性剧情杀**：P4 蓄力期间玩家必须完成一个明确目标（打出黑闪 / 打破结界），否则被斩（不可躲） | 目标达成即可活；纯演出为主 |
| **反转术式** | 恢复 | 回复**与输出共用资源**：他打得越凶，回得越慢（让玩家的压制有反馈） | 持续压制 |
| **阶段（P1→P3）** | 223~236 话的回合节奏 | 只改**攻击间隔、招式组合、霸体比例**，不改伤害（规则 8） | — |

### 4.3 魔虚罗（重点：彻底改掉）

**原作事实**（考据 §3.4）：它**没有血条**（原作从未给耐久数值，旁白用"再转 N 次就适应完成"的倒计时）；它也**被打死过两次**（涩谷被宿傩「開」、新宿被五条最大出力「茈」）；适应是**按事象逐项**的。

**新设计**：
- **适应进度条**取代血条：它对"近战 / 术式 / 领域"三类分别累积适应；条满 = 对那类免疫。
- **适应有打断窗口**：每次它"法轮转动"时有一个明显的前摇，玩家在窗口内打出高伤即可打断并**大幅推进自己的资源**（这才是"魔虚罗不是负担而是机会"）。
- **未见过的高强度一击可以击破它**（原作里它就是被「茈」一击拆掉的）——给玩家一个"攒大招秒掉它"的目标，而不是"打 33 下"。
- **它必须在注意力上是"第二威胁"而不是"第二血条"**：它的攻击频率低于宿傩，且**每次出场有明确结束条件**（适应完成 / 被击破），不无限拖时间。

## 6. 美术、画面可读性与联机

### 6.1 先说一个勘误（重要）

你给的那段剪辑 **BV1tTVw6WEzi 不是官方动画**：它是外网同人作者 **NinjaristicNinja** 做的 MMV（静止画 MAD），B 站是搬运（UP 主 唯夢WeiM，96 秒，217 万播放）。而且**新宿决战篇目前还没有被 MAPPA 动画化** —— 所以**不存在"官方分镜"可抄**，官方参照只能是漫画原作 + 前两期动画的语法（尤其涩谷事变）。
这不影响它作为美术参考的价值，但它改变了做法：我们要**从漫画分镜 + 演出语法**里取视觉语言，而不是去临摹一段不存在的动画。

### 6.2 画面"乱"的成因与预算（可执行）

现在乱的根因是**没有预算**：颜色族、特效层数、UI 区域都没有上限。建议直接落成硬约束：

| 项 | 约束 |
|---|---|
| **颜色族** | 常驻高饱和色族 **≤2**（五条 = 冷蓝系 / 宿傩 = 赤黑系），瞬时事件色 +1（放完立刻收）；**金色只准用于 UI** |
| **五条的颜色** | 不是"纯青蓝"：原作的语义是 蒼(蓝) / 赫(**红**) / 茈(**紫**)。正确做法是**同一族内的明度/色相阶梯**（冷蓝 → 青白 → 紫），否则会和宿傩撞色 |
| **黑闪** | 原作是"咒力闪**黑**"（黑色火花 + 空间扭曲），**不是红黑雷电铺满全屏** —— 后者正是这类剪辑"糊"的头号来源 |
| **混乱度判定** | 混乱度 C = 色族数 × 运动矢量数 × 叠层数，**单帧 C ≤ 12**，超过就砍最低优先级的特效 |
| **特效优先级** | P0 判定必需（命中火花/预警圈）> P1 状态（领域边界/无敌帧）> P2 氛围（粒子/尘埃）> P3 装饰（光斑/泛光）> P4 其它。**超预算时从 P4 往下砍** |
| **UI 安全区** | 画面上方只放血条/计时，中下方只放同步轴类信息（现在这块最挤）；同一时刻**最多两处**文字提示 |
| **焦点外降级** | 非焦点对象统一降到 65% 亮度 / 40% 饱和，把对比度留给"我该看的东西" |

### 6.3 相机与建模

- **相机分两套**：战斗机位（稳定、可读、不抢视线）与演出机位（分镜级，只在演出时用）。现在的问题是两者混在一起，打斗中镜头还在"表演"。
- **建模路线**（见 §8 的拍板项）：短期建议**继续程序化几何体**（零资源、秒加载、可控），但补上**剪影规范**（角色在纯黑背景下的识别度、出手前的姿态可辨）与**骨节动画**（现在的问题不是"形状不好"，是"动作僵、看不出在出什么招"）。
- 长期如果要上真正的低模资产（glTF），要提前决定资源管线与版权边界（同人非商业本项目一直守着的线）。

### 6.4 联机（两人房间号 PK）

结论（详见 \`research/D-netcode.md\`）：**不需要自建游戏服务器**。

- **方案**：WebRTC DataChannel 直连 + **主机权威**（一方浏览器算判定）+ **固定 60Hz 逻辑帧** + 客机本地预测。
- **v0（零后端）**：手动交换连接码（复制粘贴/二维码）就能开打 —— 一天能验证通不通。
- **v1（房间号）**：Cloudflare Worker + Durable Object 免费额度做 6 位房间号匹配；**DO 只当信令，绝不转发 60Hz 数据**。
- **中继兜底**：NAT 穿透失败时用免费 TURN（Metered Open Relay 20GB/月，够 110~280 小时）。
- **不要做确定性帧同步/回滚**：现有逻辑层有 Math.random、可变时间步、无状态导出，且 JS 的三角/幂函数是近似实现 —— 让主机一个人算更务实（想升级回滚，前提是先把固定帧与状态导出做好）。
- **对架构的硬要求**：从 M0 就要 sim/view 分离、固定帧、输入包可序列化。**这是"要不要重做"的另一个决定性理由**：现在的架构做不了联机。

**新项目第一天就要有 smoke + acceptance + 一个能跑真按键的探针**，否则做到第三周就没法判断手感有没有变差。
