## 二、相机：取景求解器（这是本任务的核心技术资产）

### 2.1 占屏比例反推距离（fov 解耦）
小孔成像：`画面高度 = 2·d·tan(fov/2)`。想要"角色占屏高度 = frac"，就反解

```
d = 角色身高 / (2 · tan(fov/2) · frac)
```

这条式子让**占屏比例与 fov、与角色身高都解耦**：改 fov、换角色、换画幅都不用重调距离常数。
代码：`camDistForFrac(frac, fov)`。

- 目标比例：贴身 0.32 → 拉开 0.27（解析值；验收口径实测约 ×1.15~1.2）
- 硬边界：`fracMin = 0.22`（竖屏放宽到 0.165）、`fracMax = 0.46`
- 闭环微调：每帧用投影矩阵实测"脚底→头顶"的 NDC 高度，偏出区间就 ±10% 内慢修（`camFracFix`），保证姿态变化时也落在区间里。

### 2.2 fov 解耦（重要：与 mobile.js 的耦合点）
`src/mobile.js` 会按画幅直接写 `godCam.fov`（竖屏放宽到 ~59.6°，否则视野不够用）。
如果相机模块死守 `CAM_FOV_BASE = 44`，竖屏下"公式算的距离"和"实际画幅"就对不上（实测占屏只剩 20.8%）。
现在的做法：**每帧检测 `godCam.fov` 是否被我以外的代码改过（对比上一帧我写入的值），改过就采纳为新基准 `camFovBase`**，用它反推距离；设计镜头只在基准上叠加偏移。
→ 任何画幅、任何外部 fov 调整，占屏公式都成立。

### 2.3 斜侧 3/4 与窄画幅转轴
- 宽屏：镜头绕到"选手背后偏 24°"（`CAM_YAW_SIDE = 0.42`），俯角 17.8°（`CAM_PITCH_DESIGN = 0.31`）。
- 竖屏：`PerspectiveCamera.fov` 是垂直 FOV，aspect≈0.46 时水平半 FOV 只有 ~10.5°，斜侧站法会把对手挤出画面。
  引入 `camNarrow = clamp((1.3 - aspect)/0.75, 0, 1)`：
  - 斜侧角收窄到 `0.42 × (1 - 0.72·narrow)` ≈ ±6.7°
  - 俯角 +0.10·narrow 补纵深分离
  - 占屏下限放宽到 `0.22 × (1 - 0.25·narrow)`

### 2.4 水平收敛反解（保证对手也在画面里）
把"对手 - 选手"向量投到相机右轴与视线方向：

```
perp  = e·right        // 横向偏移
along = e·forward      // 纵深分量
need  = |perp| / tan(水平半FOV × 0.82) - along
dist  = max(占屏距离, need)  并 clamp 到区间
```

横竖屏同一套代码自适应，不用给每种屏幕调常数。窄画幅系数 < 0.02 时整段跳过，宽屏行为与之前逐帧一致。

### 2.5 遮挡规避（候选机位搜索，按优先级）
建筑是 InstancedMesh，没有独立 Mesh 可 raycast，所以用**解析法线段×圆柱求交**（每 0.3 秒重建 3~10 个候选楼的 (x, z, r, h) 摊平数组，每帧零分配）。
被挡时的处理不是"无脑拉近"（实测那样会把角色怼成 85% 满屏特写），而是按优先级在候选机位里挑第一个视线通畅的：

| 优先级 | 动作 | yaw 偏移 | pitch 偏移 | 距离乘数 | 构图代价 |
|---|---|---|---|---|---|
| 1 | 原机位 | 0 | 0 | 1 | 0 |
| 2 | 抬高 | 0 | +0.22 | 1 | 0.04 |
| 3 | 明显抬高 | 0 | +0.45 | 1 | 0.10 |
| 4/5 | 侧后绕 | ±0.55 | +0.12 | 1 | 0.18 |
| 6/7 | 大幅侧绕 | ±1.0 | +0.2 | 1 | 0.32 |
| 8 | 拉近（最后手段） | 0 | +0.12 | 0.62 | 0.26 |

- 评分 = 通畅度 − 构图代价 + **迟滞项**（偏向上一帧正在用的规避动作，避免在"挡住/没挡住"之间来回甩镜头）
- 都不通畅才按命中点拉近，下限 `CAM_DIST_MIN = 3.4m`
- 规避偏移本身也做平滑（被挡 7/s 快进，恢复 1.8/s 慢出）

### 2.6 设计镜头（技能/黑闪/领域/对撞/胜负）
同一套"偏移量叠加"结构，任何设计镜头都被 `[fracMin, fracMax]` 夹住，**丢不掉角色**：

| 事件 | 时长 | 效果 |
|---|---|---|
| 术式释放 | 0.34s | 距离 ×(1-0.07)，fov +2.4，轻微侧摆 |
| 黑闪 | 0.62s | 距离 ×(1-0.075)，fov −4（压近收窄，做出顿帧冲击），俯角略降 |
| 领域展开 | 2.1s | 前 22% 快速拉远到 1.45× + 抬 0.17 + fov +6（看得到领域全貌），其余缓慢收回 |
| 领域对撞 | 持续 | 注视点 62%/38% 偏向双方中点，俯角 0.42，目标占屏 0.30-0.40，缓慢环绕 |
| 胜负 | 持续 | 绕角色 0.2 rad/s 环绕定格，占屏 0.33 |

### 2.7 跟随平滑（不晕）
- 注视点指数平滑（战斗 14/s、跳跃 >4.5m 时降到 5.5/s 防瞬移；标题 3/s）
- 相机位置 = 平滑注视点 + 精确偏移（不做二次 lerp），构图永远准
- 距离：拉近 11/s（躲遮挡要快）、推远 2.4/s（慢，避免自动变焦感）
- 自动回正有 **0.85 rad 死区**（小偏差不转，跑动时画面不漂），玩家动过镜头 1.1s 内不抢
- 实测每帧最大变化：yaw 0.005 rad、pitch 0.001 rad、距离 0.10m（150FPS 下连续采样 900 帧，覆盖近战/领域/对撞切换）

### 2.8 诊断接口 `window.__CAMUI`（只读，验收可直接读）
`state / frac(占屏%) / occl(遮挡强度) / occluded / dist / distTarget / yaw / pitch(基础角) / useYaw / usePitch(生效角) / avoid[规避偏移] / fov / shot(当前设计镜头) / focus(双方距离) / blockers(候选楼数) / userHold`
（`window.__SS.cam` / `activeCamera` 原样保留）

## 五、遗留问题（如实记录，没做到位的地方）

1. **距敌 12–20 米时对手会出画**（水平视野装不下）。
   处理：出画时用离屏指示器给方向和距离；AI 会主动逼近。但"既要角色占屏 35%+、又要 20 米外两人同框"在几何上不可能，这是取舍不是 bug。若最终验收要求"永远同框"，需要把目标占屏降到 ~15%（角色会重新变成看不清的小人），需要产品决策。
2. **3D 黑闪 callout 仍会压到角色/HUD 顶部**（`fx.callout({text:'黑闪', sub:'BLACK FLASH'})`，vfx-combat 写域）。
   我只把 DOM banner 挪开了并在戏剧排面里避免中下部；3D callout 贴在世界坐标（角色头顶 +1.2m），近景时会顶到画面上部。**建议 vfx-combat 把它改成"屏幕空间上方偏移 + 缩放上限"或改到角色侧后**。
3. **窄画幅的自动回正死区**沿用宽屏的 0.85 rad，竖屏侧向偏移本来就小，手感上更"黏"一点；没有为竖屏单独调（缺少真人手感验证）。
4. **标题画面在竖屏只环绕五条悟**（两人相距 32m，窄视野装不下两人的同时还要保证玩家角色在画面内）。属于取景取舍。
5. **`mobile.js` 直接写 `godCam.fov`** 是跨模块耦合：我现在会"采纳"它的改动，不会打架，但 FOV 的事实来源有两个（mobile.js 按画幅 + camera.js 按设计镜头）。更好的做法是 mobile.js 只设一个基准值（如 `window.__CAM_FOV_BASE`），由 camera.js 统一写 `godCam.fov`。已同步 Lead 与 mobile-ship。
6. **触屏小字补丁写在 styles.css**（`html.is-touch #hud #ability-bar .ab-cost`），本质是覆盖 mobile.css 的 clamp 下限。更干净的做法是 mobile-ship 直接改自己的下限。
7. **未做真人手感/晕动症测试**：平滑度是数值验证（每帧增量上限）+ 我自己的主观观察，没有长时间连续游玩的体感评估。
8. **中途竖屏引导层（mobile-ship 的「横屏更爽」）挡在标题按钮上**，导致 Lead 的 mobile 验收一度把"标题镜头"当成"战斗镜头"误判为 P0。已用证据澄清，Lead 已修 harness（JS click + 进战斗断言 + 关引导层）。

## 六、用户反馈回归修复：「镜头不如原版，没有在打新宿对决的感觉」

用户原话：「镜头感觉没有原来的好」「原来的问题虽然多，但真有一种在打新宿对决的感觉」。
对照物 = 根目录 `新宿决战.html` 里的原版 `updateGodCam`：俯角 0.62(≈35°)、距离 clamp(6+sep×0.95, 12, 40)、跟随 9、注视点是 0.55/0.45 的双方加权中点。

### 6.1 改了什么（对照原版）

| 项 | 原版 | 我上一版 | 现在 | 理由 |
|---|---|---|---|---|
| 俯角 | 0.62 (35°) | 0.31 (17.8°) | **0.50 (28.6°)** | 原版的上帝视角能同时看清双方走位与街区；17.8° 视野被压成一条线、看不见战场。28.6° 折中：保住战场信息量，人物也不被俯角压扁 |
| 距离依据 | 6+sep×0.95 (12~40m) | 占屏 0.32 | **占屏 0.22（≈9m）** | 保留"解方程"的优势，同时把人拉远一档；实测角色占屏 37% → 31.5% |
| 跟随系数 | 9 | 14 | **10** | 14 太黏、镜头贴着角色转没有呼吸感；10 保留一点滞后 |
| 偏航 | 基本固定（旁观视角） | 死区 0.85 / 速率 1.3 | **死区 1.3rad(75°) / 速率 0.85** | 原版方位稳定，玩家才有"这是新宿那个路口"的地点感；上一版敌人一绕就把整个街景转走 |
| 注视点 | 双方加权中点 (0.55/0.45) | 永远=玩家 | **玩家 + 朝对手偏移（上限半屏宽 40%）** | 拿回决斗对位感：两人对称落在画面左右，而不是"玩家居中、对手贴边"（Q 锁定时偏移升到 0.7） |
| 对撞机位 | 中点 + 俯角 0.56 | 俯角 0.42 / 占屏 0.34 | **俯角 0.55 / 占屏 0.22~0.30** | 两人 + 领域球一起进画面（实测 box 40.2%/43.0%，中心 +0.13/−0.00） |

### 6.2 顺带修掉的两个真实 bug

1. **闭环校准符号写反（我自己引入的回归）**：`camFracFix` 原为 `fix = fracT/measured`，而 `measured ∝ 1/距离` —— 这是**正反馈**，距离会一路漂到钳位边界（实测把角色顶到 48% 占屏）。已改为乘法微调 `fix *= measured/fracT`（每帧 ±6%，总权限 0.88~1.14）。
2. **"角色看得见、但半块屏幕被糊住"漏检**：遮挡探针原来只测"角色胸口→相机"一条线。现在补了**视锥左右边缘侵入检测**（沿画面左右边缘各打一条水平射线，命中距离 < 0.6×机位距离即判侵入并扣分），并把 **灯柱/信号杆也纳入遮挡体**（实例矩阵一次性摊平成 (x,z,r,h)；细杆只参与角色视线判定、不触发边缘判定，避免镜头对着街灯乱躲）。规避俯角上限从 1.25 收到 0.78 rad(45°)，否则会变成纯俯视图、占屏掉到 12%。

### 6.3 回归验证（改后重跑）
